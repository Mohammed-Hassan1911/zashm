# النسخ الاحتياطي والاسترجاع — ZASHM

> آخر تحديث: 2026-11-10. الملف ده يخص **بيانات الإنتاج** (Supabase). لا يحتوي على أي مفتاح أو كلمة سر.

---

## 1. إيه اللي بيتاخد باك اب

`scripts/backup-data.mjs` بيسحب الجداول التشغيلية كلها بمفتاح service-role ويحفظها JSON:

| الجدول | المحتوى |
|---|---|
| `products` | المنتجات كاملة (بما فيها `variantStock` و`active` و`tags`) |
| `orders` | كل الأوردرات (بنود، عناوين، أرقام، حالات) |
| `users` | حسابات الأدمن/الستاف وأدوارهم و`session_version` |
| `coupons` | الكوبونات وحدود الاستخدام |
| `product_reviews` | المراجعات |
| Storage (`products` bucket) | manifest بالأسماء والأحجام، و`--with-images` بينزّل الصور نفسها |

**مش متغطي (بشكل مقصود):**

- **كلمات سر الأدمن** — دي في `auth.users` ومش متاحة من REST API. لو المشروع اتمسح، تعيد إنشاء الحسابات بكلمة سر جديدة.
- **الـSchema نفسه** — محفوظ في `supabase/*.sql` و`git` هو الباك اب بتاعه.
- **متغيرات Vercel** (`SESSION_SECRET`, `TELEGRAM_*`, `UPSTASH_*`) — لازم نسخة منها في مكان آمن عندك.

## 2. إزاي تشغّله

```bash
npm run backup -- --with-images     # الجداول + الصور
npm run backup                      # الجداول فقط (أسرع)
npm run backup -- --dry-run         # يعرض الخطة بدون كتابة
npm run backup -- --keep 8          # يحتفظ بآخر 8 نسخ ويمسح الأقدم
npm run backup -- --out ~/zashm-backups
```

المكان الافتراضي: `backups/<UTC timestamp>/` جوه المشروع، ومضاف لـ`.gitignore`.

كل نسخة فيها:

```
backups/2026-11-10T00-07-44Z/
├── products.json
├── orders.json
├── users.json
├── coupons.json
├── product_reviews.json
├── manifest.json        # العدد + SHA-256 لكل ملف + حالة الصور
└── storage/             # مع --with-images
```

**الضمانات:**

- بيسحب **كل** الصفوف مش أول 1000 بس (PostgREST بيقص الصفحة عند 1000).
- بعد الكتابة بيقرأ الملف تاني ويتأكد إن عدد الصفوف مطابق.
- لو أي جدول فشل، الأمر بيرجع **exit 1** وبيكتب «incomplete» — مفيش نسخة ناقصة بتعدّي كأنها ناجحة.
- المفتاح نفسه مش بيتكتب في أي ملف ولا بيتطبع في اللوج (بيطبع الـhost بس).

## 3. الأمان

النسخة فيها **أسماء وتليفونات وعناوين عملاء**. القواعد:

- متحطهاش على GitHub ولا في الشات ولا في Drive عام.
- خزّنها على جهازك أو قرص مشفّر.
- `--keep` بيمسح النسخ القديمة — سيب على الأقل آخر نسختين.

## 4. إزاي ترجّع البيانات

### الحالة أ: المشروع موجود والبيانات اتشالت بالغلط (أوردر/منتج واحد)

أسهل طريق من الداشبورد: Table editor → الصف → Insert، أو من نسخة JSON:

```bash
node -e "
const rows = require('./backups/2026-11-10T00-07-44Z/orders.json');
// اطبع الصف المطلوب بس، وبعدها أضفه يدويًا من الداشبورد
console.log(JSON.stringify(rows.find(r => r.id === 'ZSH-...'), null, 2));
"
```

### الحالة ب: المشروع اتمسح أو الداتابيز اتلفت

1. أنشئ مشروع Supabase جديد.
2. طبّق ملفات `supabase/*.sql` بالترتيب الموثّق في `docs/production-remediation-handoff.md` (نفس ترتيب الإنتاج).
3. أعد إدخال الصفوف من نسخة الباك اب بمفتاح service-role (الأوردرات أولًا، بعدها المنتجات/الكوبونات/المراجعات/المستخدمين).
4. أنشئ حسابات الأدمن من Supabase Auth بنفس الإيميلات، وحدّث `public.users` لتطابقها.
5. ارفع الصور من `backups/.../storage/` لنفس المسارات في bucket `products`.
6. حدّث متغيرات Vercel (`SUPABASE_*`, `SESSION_SECRET` جديد، Telegram) وأعد النشر.

> الترتيب مهم: `orders` بيشير لمنتجات؛ أعد المنتجات الأول لو هتتحقق من التكامل.

## 5. الجدولة

**دلوقتي (مجاني):** شغّل `npm run backup -- --with-images`:

- قبل أي تغيير خطير (migration، حذف منتجات، تنظيف أوردرات).
- **أسبوعيًا** على الأقل.
- بعد أي يوم فيه أوردرات كتير.

**البديل التلقائي (يحتاج موافقة):**

- **Supabase Pro**: نسخ يومية محفوظة 7 أيام + Point-in-time recovery اختياري + مفيش إيقاف للمشروع عند الخمول.
- **GitHub Action مجاني**: جدولة يومية تشغّل السكربت وتحفظ النسخة كـartifact — بس ده معناه إن مفتاح service-role يتحفظ في GitHub Secrets.

## 6. ملاحظة عن snapshot المنتجات (مش باك اب)

`public/catalog-snapshot.json` مش باك اب داتابيز — ده **نسخة عرض** للمنتجات بس، عشان المتجر ميبانش فاضي لو Supabase وقع.

**التحديث بقى تلقائي مع كل نشر.** `vercel.json` بيشغّل قبل البناء:

```
node scripts/resilience-sync.mjs --best-effort --stamp && npm run build
```

يعني كل deploy بيقرأ `products_public` ويكتب snapshot جديد + بينزّل الصور في `public/media` جوه ناتج البناء:

- **منتج جديد** → يظهر في الـsnapshot تلقائيًا مع أول نشر بعده.
- **منتج متمسح** → يختفي تلقائيًا.
- **منتج في `scripts/resilience-exclude.json`** → مستبعد دايمًا.
- **لو Supabase واقع وقت البناء** → `--best-effort` يخلّي البناء يكمل بالنسخة المحفوظة في git بدل ما يفشل النشر.
- `--stamp` بيخلي `generatedAt` يتكتب دايمًا وقت البناء، فتقدر تتحقق من النسخة المنشورة إنها اتحدّثت فعلاً.

التشغيل اليدوي لسه موجود لو عايز تشوف النتيجة قبل النشر:

```bash
npm run resilience:sync            # snapshot + صور
npm run resilience:sync -- --prune # + مسح صور المنتجات المحذوفة
```

> ملاحظة: `npm run build` المحلي **مش** بيعمل sync — التحديث مربوط بأمر البناء على Vercel فقط.

| العنصر | الرقم |
|---|---|
| حجم المنتج الواحد في الـsnapshot | ~1 كيلوبايت (حتى 3 كيلوبايت بوصف وصور كتير) |
| 100 منتج | ~0.1–0.3 ميجا |
| 1,000 منتج | ~1–3 ميجا (مضغوطة ~200–400 كيلوبايت) |
| 5,000 منتج | ~5–15 ميجا — **قرب الحد العملي** |

الحد الحقيقي مش التخزين، هو **المتصفح**: النسخة بتتحفظ في `localStorage` اللي سقفه ~5 ميجا للموقع، والملف بيتحمّل بس وقت فشل Supabase. فالحد العملي **~1,000–2,000 منتج**؛ فوق كده الأفضل pagination أو الاعتماد على قاعدة البيانات مباشرة.

الأوردرات والعملاء والكوبونات **مش** في الـsnapshot — دول في الباك اب بتاع القسم 1.
